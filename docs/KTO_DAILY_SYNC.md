# KTO 일일 동기화 및 상세기능별 요청 한도

## 실행 방식

`KTO_CONTINUOUS_SYNC_SCHEDULE_ENABLED=true`이면 한국 시간 오전 8시 이후 날짜별 동기화 사이클을 진행한다. 기본 예약식은 `0 */10 8-23 * * *`, 시간대는 `Asia/Seoul`이다. 10분마다 하는 것은 작업 접수 가능 여부 확인이며 같은 데이터를 10분마다 전수 수집하는 것이 아니다. 날짜와 단계별 예약 키가 중복 사이클을 막는다. 기존 환경에 일요일 cron이 명시되어 있다면 배포 시 새 예약식으로 변경해야 한다.

국문 목록 → 영문 목록 → 축제 → 공모전 사진 → 관광사진 → 연관 관광지 → 상세 보강 순으로 실행한다. 각 단계는 작은 작업으로 이어 처리하며 전역 활성 작업 슬롯은 하나다. 완료 또는 당일 실패한 단계는 그날 다시 시작하지 않고 다음 단계로 이동한다. 따라서 한 오퍼레이션의 한도가 소진되어도 다른 오퍼레이션의 작업은 진행할 수 있다. 모든 단계가 끝나면 다음 날까지 새 사이클을 만들지 않는다.

이 모드에서는 기존 상세 일일 800곳 예약과 연관 관광지 재개 예약을 중복 실행하지 않는다. `KTO_CONTINUOUS_SYNC_REQUEST_BUDGET`의 800페이지 제한도 사용하지 않는다. 이전 모드를 별도로 사용할 때만 기존 상세 예산이 적용된다.

## 설정: 기본값 하나, 예외 목록 하나

- `KTO_DAILY_REQUEST_LIMIT=1000`: 별도 지정이 없는 모든 상세기능의 하루 기본 한도.
- `SPRING_APPLICATION_JSON`: 운영계 승인 후 한도가 달라진 상세기능만 `koready.kto.quota.limits`에 지정한다. 이 환경변수에 기존 설정이 있다면 전체 JSON을 덮어쓰지 않고 해당 경로를 병합한다.

예: 공통정보만 10000회, 이미지 정보만 5000회로 승인된 경우:

```json
{"koready":{"kto":{"quota":{"limits":{"kor-detailcommon2":10000,"kor-detailimage2":5000}}}}}
```

| 설정 키 | 서비스 / 상세기능 |
|---|---|
| `kor-areabasedsynclist2` | KorService2 / areaBasedSyncList2 |
| `eng-areabasedsynclist2` | EngService2 / areaBasedSyncList2 |
| `kor-searchfestival2` | KorService2 / searchFestival2 |
| `kor-detailcommon2` | KorService2 / detailCommon2 |
| `kor-detailintro2` | KorService2 / detailIntro2 |
| `kor-detailinfo2` | KorService2 / detailInfo2 |
| `kor-detailimage2` | KorService2 / detailImage2 |
| `kor-searchkeyword2` | KorService2 / searchKeyword2 (기존 초기등록 경로) |
| `photo-award-phokoawrdsynclist` | PhokoAwrdService / phokoAwrdSyncList |
| `photo-gallery-gallerylist1` | PhotoGalleryService1 / galleryList1 |
| `related-tour-areabasedlist1` | TarRlteTarService1 / areaBasedList1 |

각 키는 독립된 한도다. 국문과 영문의 같은 오퍼레이션 이름도 합산하지 않는다. 0으로 지정하면 해당 상세기능을 중단한다. 승인받은 수치를 설정하며 운영계 전환 자체만으로 자동 증액하지 않는다. 미사용 API를 한도 소진 목적으로 새로 호출하지 않는다.

## 요청 집계 및 중단

모든 KTO RestClient에 요청 직전 차단기를 적용한다. `kto_daily_request_usage`에 KST 날짜와 서비스·오퍼레이션별 예약 횟수를 원자적으로 증가시킨 후에만 전송한다. 예약 트랜잭션은 작업 트랜잭션과 독립적이므로 실패·롤백·재시작이 예산을 복원하지 않는다. 재시도도 매번 차감한다. 동시 서버가 같은 DB를 사용하면 같은 카운터를 공유한다.

예약 횟수는 성공 응답 수와 다르다. 예약 후 전송 전에 중단되거나 네트워크 오류가 난 경우에도 보수적으로 사용량에 포함한다. 인증키·전체 URL·원문은 한도 테이블에 저장하지 않는다. 기존 `open_api_call_logs`는 성공 수집 증빙 및 원본 스냅샷 연결에 계속 사용하며, 스냅샷 재사용으로 중복 제거된 로그 수를 정확한 요청 예산으로 간주하지 않는다.

최초 마이그레이션 당일에는 기존 요청을 완전히 재구성할 수 없으므로 현재 사용하는 상세기능을 당일 차단한다. 다음 KST 날짜부터 새 카운터로 시작한다. 이는 호출 수를 허위로 기록하지 않으면서 배포 당일 초과 요청을 방지하기 위한 조치다.

자체 한도가 소진되면 외부 요청 없이 `KTO_QUOTA_EXCEEDED`로 작업을 종료한다. 공사의 한도 초과 코드 22도 즉시 중단하며 반복 재시도하지 않는다. 전송 오류와 일시적인 서버 오류의 기존 제한적 재시도는 유지한다. 같은 인증키를 다른 서버·개발 PC에서 사용한 요청은 이 DB가 알 수 없으므로, 키 사용처를 통합하고 공사 통계와 대조해야 한다.

## 재개와 최신성

- 목록·사진·연관 관광지는 직전 일일 사이클의 마지막 실패 청크 파라미터로 다음 날 재개한다. 같은 날 실패를 무한 재접수하지 않는다. 관련 없는 관리자 수동 작업을 자동으로 재실행하지 않는다.
- 실패 청크에서 이미 성공한 일부 페이지는 재조회될 수 있다. 기존 content ID 기반 upsert와 원본 해시로 중복 적재를 방지한다. 페이지 데이터가 수집 중 변할 수 있으므로 하루 호출은 전체 데이터의 당일 갱신 완료를 의미하지 않는다.
- 상세는 다음 날 ID 0에서 다시 대상을 선정하되 완료 체크포인트와 갱신 기한으로 이미 처리한 장소를 건너뛴다. 국문 목록의 원본 해시가 바뀐 장소는 상세 갱신 기한을 앞당겨 재수집 대상으로 만든다. 변경이 감지되지 않은 상세의 정기 재확인은 기존 30일 주기를 유지한다.
- 상세 한 장소를 완료하려면 공통·소개·반복·이미지 정보가 모두 필요하다. 네 상세기능 중 하나가 먼저 소진되면 그 장소의 완전한 갱신은 다음 날로 넘어간다. 남은 다른 기능의 한도를 억지로 소진하지 않는다.
- 연관 관광지는 최신 제공 완료월을 조회하는 기존 방식(기본 직전 월)을 유지한다. 월별 통계를 매일 조회한다고 일별 통계로 바뀌지는 않는다.
- 사진의 장소 연결 및 사용자 노출 승인은 기존 관리자 정책을 유지한다. 원본 수집 성공을 신규 사진의 공개 승인과 동일시하지 않는다.

## 적용과 점검

공통 quota 설정은 test/local/staging/prod 모두 동일한 기본값을 사용한다. 자동 사이클은 기본 비활성이며 의도한 실행 환경에서만 켠다. 테스트는 외부 KTO 대신 가짜 HTTP 및 Testcontainers MySQL을 사용한다. 실제 키는 설정 저장소에서만 관리한다.

배포 시 기존 cron과 시간대를 확인하고 일요일 예약식을 매일 08시 이후 예약식으로 바꾼다. 자동 사이클을 켠 환경에서 운영자 수동 실행도 같은 요청 카운터를 소비한다. 설정 반영 후 첫 실행 날짜의 단계별 배치 상태, 요청 예약 수, 실제 호출 로그, 원본 변경으로 인한 상세 재수집을 확인해야 운영 적용 완료로 보고할 수 있다.

실패나 장기 미갱신은 관리자 작업 목록에서 확인한다. 자동 경보 전송, 모든 원본의 하루 내 갱신 보장, 공사 승인 여부는 이 구현이 제공하지 않는다. 신청서에는 구현·배포·실행 검증 상태를 구분해서 기재한다.
